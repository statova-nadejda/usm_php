# Лабораторная работа №7. Шаблонизация

## Цель работы

Освоить принципы шаблонизации в PHP, как с использованием нативных PHP-шаблонов, так и с применением готового шаблонизатора. Улучшить структуру проекта, разделив логику обработки данных и представление.

## Условие

Продолжите разработку проекта из лабораторной работы №6, разделив его на слои: логику и представление. Работа выполняется в два этапа - сначала вы реализуете собственный механизм шаблонизации, затем подключаете Twig и реализуете ту же функциональность через него.
## Шаг 1. Рефакторинг. Нативные PHP-шаблоны

На этом шаге был переписан проект из лабораторной работы №6 путем разделения кода на логику и представление.

- **Логика**: Это PHP-файлы, которые получают запросы от пользователя, читают или записывают данные и готовят переменные для показа.
- **Представление**: Это отдельные файлы с расширением .php, которые только показывают данные. Они не содержат кода для обработки.

Структура проекта первой части работы:

```
project/
├── templates/
│   ├── layouts/
│   │ ├── form-layout.php         # Общий макет формы для добавления записи
│   │ └── table-layout.php        # Общий макет со списком записей
│   ├── pages/
│   │ ├── trip-form.php          # Шаблон страницы формы для добавления записи
│   │ └── trip-table.php         # Шаблон страницы таблицы со списком записей
├── src/
│   ├── Contracts/               # Интерфейсы для шаблонизатора
│   ├── Models/                  # Модели данных
│   ├── Validators/              # Валидация форм
│   ├── HtmlEscaper.php          # Класс для экранирования
│   ├── LayoutRenderer.php       # Рендер с layout
│   ├── Renderer.php/            # Базовый PHP-рендерер
│   ├── View.php                 # Объект представления (шаблон + данные)
├── styles/                      # CSS стили
├── main.php                     # Точка входа: отображение формы
├── submit.php                   # Обработка POST-запроса формы
├── trips.php                    # Точка входа: отображение таблицы поездок
├── trips.txt                    # Хранилище данных (файл с поездками)

```

В этом проекте шаблоны находятся в папке `templates/`, а логика в `src/`.


```php
<?php

require_once __DIR__ . '/vendor/autoload.php';

use User\PhpLab07\HtmlEscaper;
use User\PhpLab07\Renderer;
use User\PhpLab07\LayoutRenderer;

use User\PhpLab07\View;
use User\PhpLab07\TwigRenderer;

session_start();

$errors = $_SESSION['errors'] ?? [];
$old = $_SESSION['old'] ?? [];

unset($_SESSION['errors'], $_SESSION['old']);

$escaper = new HtmlEscaper();
$baseRenderer = new Renderer(__DIR__ . '/templates);
$renderer = new LayoutRenderer($baseRenderer, 'layouts/form-layout');

$renderer = new TwigRenderer(__DIR__ . '/templates');

$view = new View('pages/trip-form', [
    'errors' => $errors,
    'old' => $old,
    'escaper' => $escaper,
]);

echo $renderer->render($view);
```
Здесь в файле main.php мы готовим данные, которые попадут в шаблон. Затем создаем объект View с указанием шаблона, который нужно отобразить, и передаем ему массив данных. Наконец, рендерим шаблон и выводим результат.

## Шаг 2. Использование готовых шаблонизаторов

### 2.1. Установка и настройка Twig

Twig устанавливаем с помощью Composer. В файле composer.json добавляет зависимость:

```json
{
    "require": {
        "twig/twig": "^3.0"
    }
}
```

Затем запускается `composer install`.

### 2.2. Переписывание шаблонов с Twig

Те же шаблоны переписываем с помощью синтаксиса Twig. Twig - это отдельный язык шаблонов, который не позволяет выполнять произвольный PHP-код, что делает его безопаснее и чище.
Данные передаются в Twig, который обрабатывает шаблон и далее создается layout через extends. Например:

```twig
{% extends "layouts/form-layout.twig" %}

{% block content %}
    <form action="submit.php" method="POST">
        <div>
            <label for="title">Title *</label>
            <input
                    type="text"
                    name="title"
                    id="title"
                    value="{{ old.title|default('') }}"
                    class="{{ errors.title is not empty ? 'error-input' : '' }}"
            >

            {% if errors.title is not empty %}
                <p class="error-text">{{ errors.title }}</p>
            {% endif %}
        </div>
```

### 2.3. Использование возможностей Twig

В Twig используют наследование шаблонов. Например, layout.twig:

```twig
<!DOCTYPE html>
<html>
<head>
    <title>{% block title %}Мой сайт{% endblock %}</title>
</head>
<body>
    {% block content %}{% endblock %}
</body>
</html>
```

Затем в другом шаблоне:

```twig
{% extends "layout.twig" %}
{% block title %}Форма поездки{% endblock %}
{% block content %}
    <!-- содержимое формы -->
{% endblock %}
```

Это позволяет повторно использовать общий макет.

## Шаг 3. Дополнительные функции

Фильтр в Twig — это специальная функция, которая применяется к данным прямо в шаблоне для их преобразования или форматирования перед выводом. Он позволяет отделить логику обработки данных от HTML-разметки и сделать шаблоны более читаемыми.
```php
<?php
{{ price|currency('EUR') }}
```

Значение price перед выводом будет обработано фильтром currency, который преобразует число в строку с валютным символом и нужным форматом. Пользовательские фильтры добавляются в приложении на уровне настройки Twig: 

```php
$this->twig->addFilter(new TwigFilter('currency', function ($amount, string $currency = 'EUR') {
    $amount = (float) $amount;

    $symbols = [
         'EUR' => '€',
         'USD' => '$',
         'GBP' => '£',
        ];

        $symbol = $symbols[$currency] ?? $currency;

        return $symbol . number_format($amount, 2, '.', ',');
```

## Контрольные вопросы

1. **В чём отличие нативных PHP-шаблонов от шаблонизатора Twig? Какие преимущества и недостатки у каждого подхода?**

Нативные PHP-шаблоны - это обычные .php файлы, где HTML и PHP-код написаны вместе в одном месте. Но поскольку логика и вёрстка перемешаны в одном файле, это может привести к неразберихе и сложностям при поддержке. 

Twig - это отдельный язык шаблонов, который специально создан только для отображения данных. Он намеренно не даёт писать сложную логику прямо в шаблоне, что заставляет делать всё правильно.

У нативных PHP-шаблонов главное преимущество в том, что ничего не нужно устанавливать и учить, используется PHP. Но главный минус в том, что очень легко начать писать логику прямо в шаблоне, и вскоре смешиваются SQL-запросы, условия и HTML-теги. Также безопасность на разработчике - нужно вручную писать htmlspecialchars() везде, иначе XSS-уязвимости.

У Twig главное преимущество - автоматическое экранирование переменных (защита от XSS по умолчанию) и чистый читаемый синтаксис. Дизайнер может работать с .twig файлом, не боясь сломать логику. Минус - нужно установить через Composer и потратить время на изучение синтаксиса, хотя он простой.

2. **Зачем разделять логику и представление в проекте? Какие проблемы могут возникнуть, если смешивать их в одном файле?**

В веб-приложениях важно разделять бизнес-логику и представление данных. В противном случае один файл может одновременно содержать подключение к базе данных, выполнение SQL-запросов, обработку данных и HTML-разметку. Такой подход приводит к увеличению сложности кода и затрудняет его поддержку.

Основные проблемы отсутствия разделения заключаются в следующем. Во-первых, внесение изменений в интерфейс становится рискованным, так как изменение HTML может повлиять на программную логику. Во-вторых, происходит дублирование кода, поскольку одна и та же логика обработки данных используется в разных файлах. В-третьих, усложняется тестирование: невозможно изолированно проверить корректность вычислений без запуска всей страницы. В-четвёртых, диагностика ошибок становится затруднительной, поскольку сложно определить, связана ли проблема с логикой или с отображением.

При правильной архитектуре контроллер отвечает за получение и обработку данных, а шаблон - исключительно за их отображение. Это позволяет упростить сопровождение системы, повысить читаемость кода и снизить вероятность ошибок.

3. **Что такое наследование шаблонов в Twig? Как работают {% extends %} и {% block %}?**

Наследование шаблонов в Twig предназначено для повторного использования общей структуры страниц и предотвращения дублирования кода. Оно основано на принципе выделения базового шаблона, содержащего общие элементы интерфейса, такие как header, footer.

Базовый шаблон (например, base.html.twig) определяет общую HTML-структуру страницы и содержит специальные блоки `({% block %})`, которые могут быть переопределены в дочерних шаблонах.

Дочерний шаблон с помощью конструкции `{% extends %}` указывает, что он наследует базовый шаблон, и переопределяет только необходимые блоки, например содержимое страницы или заголовок.

В процессе рендеринга Twig объединяет базовый и дочерний шаблоны: сохраняет общую структуру и подставляет в неё содержимое блоков. Такой подход позволяет централизованно управлять общими элементами интерфейса. Например, изменение меню или оформления в базовом шаблоне автоматически применяется ко всем страницам, что значительно упрощает сопровождение приложения.
