# Отчёт по лабораторной работе №6
## Обработка и валидация форм в PHP


## Цель работы

Освоить основные принципы работы с HTML-формами в PHP, включая отправку данных на сервер, их обработку, валидацию, сохранение в файл и последующий вывод в виде HTML-таблицы.


## Задача

В рамках лабораторной работы было разработано мини-приложение на PHP.

Была реализована тема: **Планировщик поездок / менеджер поездок**

Пользователь имеет возможность:

- ввести данные о поездке через HTML-форму;
- отправить их на сервер;
- пройти серверную валидацию;
- сохранить запись в файл `trips.txt`;
- просмотреть все сохранённые поездки в виде HTML-таблицы;
- сортировать записи по различным полям.

Дополнительно в рамках задания была реализована ООП-архитектура и интерфейс для валидаторов. Условие лабораторной включало создание модели с минимум 6 полями, обработку формы методом POST, серверную валидацию, сохранение в читаемом формате и вывод таблицы с сортировкой.

## Шаг 1. Определение модели данных

Для проекта была выбрана модель поездки. Каждая запись о поездке содержит следующие поля:

| Поле | Тип | Описание |
|------|-----|----------|
| `title` | string | Название поездки |
| `destination` | string | Место назначения |
| `startDate` | date | Дата начала поездки |
| `endDate` | date | Дата окончания поездки |
| `description` | text | Описание поездки |
| `budget` | float / numeric | Бюджет поездки |
| `transport` | enum | Вид транспорта |


## Шаг 2. Создание HTML-формы

Для ввода данных была создана форма `TripForm.php`. Форма отправляет данные методом `POST` в файл `submit.php`.

Форма включает поля: `title`, `destination`, `startDate`, `endDate`, `description`, `budget`, `transport`.

Для поля `transport` реализован выбор одного значения из набора: `Car`, `Plane`, `Train`, `Bus`.

Ошибки валидации отображаются прямо под соответствующим полем, а ошибочные поля подсвечиваются красным цветом через CSS. При повторном отображении формы значения, которые пользователь уже ввёл, не теряются.


## Шаг 3. Обработка данных на сервере

Обработка формы выполняется в файле `submit.php`. Этот файл:

- запускает сессию;
- подключает необходимые классы валидаторов;
- создаёт объект `TripFormValidator` и передаёт в него данные из `$_POST`;
- сохраняет старые значения в `$_SESSION['old']`;
- выполняет валидацию;
- при ошибках сохраняет их в `$_SESSION['errors']` и делает редирект обратно на форму;
- при успешной валидации сохраняет данные в файл `trips.txt`.

Записи сохраняются в формате JSON, по одной записи в строке. Это соответствует требованию хранить данные в читаемом формате для дальнейшего использования.

Пример одной строки в файле:

```json
{"title":"Vacation","destination":"Italy","startDate":"2025-06-10","endDate":"2025-06-20","description":"Summer trip","budget":"1200","transport":"Plane","createdAt":"2025-06-01 14:30:00"}
```


## Шаг 4. Вывод данных

Для чтения записей из файла и отображения их в виде HTML-таблицы был создан файл `TripsTable.php`. В нём:

- читается `trips.txt`;
- каждая строка преобразуется из JSON в массив;
- все записи собираются в массив `$trips`;
- массив выводится в виде HTML-таблицы.

Для оформления таблицы используется отдельный файл стилей `table-style.css`.

## Шаг 5. Сортировка данных

В таблице была реализована сортировка по различным полям: `title`, `destination`, `startDate`, `endDate`, `budget`, `transport`, `createdAt`.

Сортировка реализована через GET-параметры `sort` и `order`. Пример:

```
TripsTable.php?sort=budget&order=asc
```

Для числовых и датовых полей применялись дополнительные преобразования: `budget` приводится к числу, даты преобразуются через `strtotime()`. Это позволяет сортировать записи корректно.


## ООП-реализация проекта

В проекте был применён объектно-ориентированный подход.

### Класс `TripRender`

Класс `TripRender` отвечает за отображение HTML-формы. Он запускает `session_start()`, получает ошибки и старые значения из `$_SESSION`, удаляет их после чтения, подключает шаблон `TripForm.php` и с помощью буферизации вывода возвращает готовый HTML. Таким образом, логика получения данных формы отделена от HTML-разметки.

### Класс `TripFormValidator`

Этот класс является центральным элементом серверной валидации. Он принимает сырые данные формы, очищает их с помощью `trim()`, формирует набор валидаторов для каждого поля, запускает проверку, собирает ошибки и отдаёт очищенные данные наружу.

### Интерфейс `ValidatorInterface`

Для унификации системы валидации был создан интерфейс:

```php
interface ValidatorInterface
{
    public function validate(array $data): ?string;
}
```

Этот интерфейс задаёт единый контракт для всех валидаторов: принять массив данных, вернуть `null` при успехе или строку с текстом ошибки при неудаче. Использование интерфейса делает архитектуру гибкой и расширяемой.

### Отдельные классы-валидаторы

В проекте были реализованы следующие классы валидаторов:

- `RequiredValidator` — проверяет, что обязательное поле не пустое;
- `LengthValidator` — проверяет длину строки для полей `title` и `destination`;
- `DateValidator` — проверяет корректность даты;
- `DateOrderValidator` — проверяет, что `endDate` больше `startDate`;
- `NumericValidator` — проверяет, что `budget` является числом;
- `TransportValidator` — проверяет, что тип транспорта входит в допустимый список.


## Как работает валидация

1. Пользователь заполняет форму и нажимает Submit.
2. Данные отправляются в `submit.php` методом `POST`.
3. Создаётся объект `TripFormValidator`.
4. Внутри него формируются валидаторы для каждого поля.
5. Метод `validate()` запускает по очереди все валидаторы.
6. Если по полю найдена ошибка, она сохраняется, а дальнейшая проверка этого поля прекращается.
7. При наличии ошибок — они и старые значения сохраняются в `$_SESSION`, выполняется редирект обратно на форму.
8. При отсутствии ошибок — запись сохраняется в файл `trips.txt`, пользователь перенаправляется на страницу формы.

Пример правил валидации:

- `title` и `destination` — обязательны, длина от 2 до 50 символов;
- `startDate` и `endDate` — обязательны, дата должна быть корректной; дата окончания должна быть позже даты начала;
- `budget` — обязателен, значение должно быть числом;
- `transport` — обязателен, значение должно быть одним из допустимых вариантов.


## Безопасность обработки данных

При работе с формами была обеспечена защита от XSS и некорректного ввода.

**Очистка данных.** Во входных данных применялся `trim()` для удаления лишних пробелов.

**Экранирование вывода.** При повторном выводе значений формы и данных в таблице использовалась функция `htmlspecialchars()`:

```php
value="<?= htmlspecialchars($old['title'] ?? '') ?>"
```

```php
<td><?= htmlspecialchars($trip['title'] ?? '') ?></td>
```

Это предотвращало выполнение вредоносного HTML или JavaScript-кода.

**Серверная валидация.** Даже если пользователь обходил HTML-ограничения, данные всё равно проверялись на сервере в `submit.php`.

# Контрольные вопросы


## Вопрос 1. Какие существуют методы отправки данных из формы на сервер? Какие методы поддерживает HTML-форма?

В HTML-формах данные могут передаваться на сервер с использованием различных HTTP-методов, однако стандартная HTML-форма напрямую поддерживает только два метода: `GET` и `POST`. Метод `GET` передаёт данные через адресную строку браузера в виде строки запроса, что делает их видимыми пользователю. Данный метод удобно использовать в тех случаях, когда необходимо выполнить операции, не изменяющие состояние системы, например поиск, фильтрацию или сортировку данных. В разработанном приложении метод `GET` применяется при реализации сортировки таблицы поездок. При нажатии на заголовок столбца формируется ссылка с параметрами `sort` и `order`, например `TripsTable.php?sort=budget&order=asc`, после чего эти значения считываются на стороне сервера через массив `$_GET`. Таким образом, пользователь может управлять порядком отображения данных, а сама операция остаётся безопасной и не изменяет содержимое системы.

Метод `POST`, в отличие от `GET`, передаёт данные в теле HTTP-запроса, поэтому они не отображаются в адресной строке. Этот метод используется для операций, связанных с изменением данных, например при отправке формы, добавлении новой записи или обновлении информации. В данной лабораторной работе метод `POST` используется для отправки формы создания новой поездки. В HTML это реализовано с помощью конструкции `<form action="submit.php" method="POST">`, а на стороне сервера данные извлекаются через суперглобальный массив `$_POST`. Такой подход обеспечивает более безопасную передачу данных и позволяет обрабатывать большие объёмы информации.

## Вопрос 2. Какие глобальные переменные используются для доступа к данным формы в PHP?

Для доступа к данным формы в PHP используются специальные суперглобальные массивы. Основными являются `$_POST` и `$_GET`, которые позволяют получать данные, переданные соответствующими методами. В разработанном приложении массив `$_POST` используется для обработки данных формы поездки, например при создании объекта `TripFormValidator`, куда передаются все значения полей. Массив `$_GET` применяется при реализации сортировки таблицы, где из параметров запроса извлекаются значения сортировки и порядка. Кроме того, в проекте используется массив `$_SESSION`, который позволяет хранить данные между запросами. Он применяется для передачи ошибок валидации и ранее введённых значений формы обратно пользователю после неудачной отправки. Это позволяет улучшить пользовательский опыт, так как форма не очищается полностью при возникновении ошибки.

## Вопрос 3. Как обеспечить безопасность при обработке данных из формы (например, защита от XSS)?

### Что такое XSS

XSS (Cross-Site Scripting) — это атака, при которой злоумышленник вводит в форму HTML- или JavaScript-код, который затем выполняется браузером других пользователей. Например, если поле `title` содержит:

```html
<script>alert('XSS')</script>
```

и данные выводятся без экранирования, браузер выполнит этот скрипт.

### Применённые меры защиты

Для предотвращения таких атак в проекте используется функция `htmlspecialchars()`, которая экранирует специальные символы и преобразует их в безопасный текст. Эта функция применяется при выводе данных в форме и в таблице, например при подстановке старых значений в поле ввода или при отображении записей из файла. Благодаря этому даже если пользователь введёт вредоносный код, он не будет выполнен, а отобразится как обычный текст.

Кроме того, в проекте реализована серверная валидация данных с использованием класса `TripFormValidator`. Все входные данные предварительно очищаются с помощью функции `trim()`, а затем проходят проверку через набор валидаторов, реализующих интерфейс `ValidatorInterface`. Проверяется обязательность полей, длина строк, корректность дат, числовой формат бюджета и допустимость выбранного типа транспорта. Такой подход гарантирует, что на сервер попадут только корректные и ожидаемые данные, даже если пользователь попытается обойти ограничения на стороне клиента. Дополнительно используется проверка допустимых значений, например для поля `transport`, что исключает возможность передачи произвольных данных.
